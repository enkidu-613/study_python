## 起点与目标

心智模型：把“我觉得正确”变成程序能重复核验的输入与预期结果。
前置：函数返回值、异常、从同目录导入函数，以及 `__name__` 入口保护。
本章按计算器 → 手工检查 → `assert` → pytest → 字符串 → 测试目录的顺序推进。
学习独立单元的输入输出契约与异常；不要求掌握 mock、fixture、覆盖率工具或持续集成。
单元测试通常聚焦一个函数等小单元，不等于运行整个交互程序，也不能证明所有输入都正确。

## 1. Unit Tests：从可以导入的计算器开始

先按前置 01-06 节完成环境配置，参见[安装 Python 并验证环境](../03_安装Python并验证环境.md)与[运行第一个程序](../06_运行第一个Python程序与读报错.md)。
默认在独立练习目录、已激活的独立 Python 环境里操作；不要把课堂文件混入仓库现有测试。先确认解释器：

```bash
python --version
```

下面是双文件例子。第一个文件 `calculator.py`：

```python
def main():
    number = int(input("What's x? "))
    print("x squared is", square(number))


def square(number):
    return number * number


if __name__ == "__main__":
    main()
```

运行 `python calculator.py`，输入 `3`，预期输出 `x squared is 9`。
执行者是你，输入来自终端，结果也需要你观察；每改一次代码都手工输入，成本会累积。
`square` 只接收参数并返回数值，不读取键盘，这使另一段程序也能调用它。

第二个文件 `test_calculator.py`，先不用第三方库：

```python
from calculator import square


def main():
    test_square()


def test_square():
    if square(2) != 4:
        print("2 squared was not 4")
    if square(3) != 9:
        print("3 squared was not 9")


if __name__ == "__main__":
    main()
```

运行 `python test_calculator.py`，正确版本不会输出错误提示，也不会询问 `What's x?`。
调用链：测试脚本的 `main` → 测试函数 → 被测函数 `square` → 比较返回值 → 必要时打印错误。
导入时 `calculator.__name__` 不是 `"__main__"`，因此不会自动执行交互式 `main`。
“没有输出”也可能是根本没调用测试、条件写错或缺少关键案例，不能只凭沉默断定可靠。

## 2. assert：将预期写成断言

完整替换 `test_calculator.py`：

```python
from calculator import square


def test_square():
    assert square(2) == 4
    assert square(3) == 9


if __name__ == "__main__":
    test_square()
```

`assert` 是 Python 语句，不是函数；它检查后面表达式的真假。
条件为真则继续，为假则抛出 `AssertionError`；不是返回 `False` 给调用者。
`square(3)` 返回实际值，`9` 是独立给定的预期值；`==` 执行比较，不是赋值。
可写 `assert square(3) == 9, "three should square to nine"` 给失败加信息。

做一个故意破坏的小实验：只把 `calculator.py` 中的 `number * number` 改成 `number + number`。
运行 `python test_calculator.py`，第一个断言仍过，第二个断言失败，因为 `3 + 3` 是 `6`。
这说明只试 `2` 会漏掉错误；一个“刚好正确”的例子不是足够的行为证据。
失败的断言会中断当前函数；同一函数后面的断言不会继续执行。
做完实验恢复乘法。这里的“故意改错”是验证测试确实能抓错，不是正式程序的新需求。

### 为什么不一直手写 try/except？

下面仍是完整的 `test_calculator.py`，用于观察捕获失败的机制：

```python
from calculator import square


def main():
    try:
        assert square(3) == 9
    except AssertionError:
        print("3 squared is not 9")

    try:
        assert square(-3) == 9
    except AssertionError:
        print("-3 squared is not 9")


if __name__ == "__main__":
    main()
```

捕获一个断言异常后可以继续下一段检查，但每个案例都手写异常处理会重复，报告也不统一。
如果只是捕获并打印，程序还可能以成功状态结束；测试工具需要更明确的失败记录。
普通运行的 `assert` 可被 `python -O` 优化掉；不要用它代替正式的用户输入校验或权限检查。

## 3. pytest：让工具发现、调用并报告测试

以下仅是独立练习环境的安装说明，本文编写时未执行；若已安装则不必重装，不用于向 Poetry 项目环境混装依赖：

```bash
python -m pip install pytest
python -m pip show pytest
```

`pytest` 是第三方测试框架，安装名和导入名均为 `pytest`。
当前项目已有 pytest；若选择在该项目下的独立练习子目录验证，可用 `poetry run python -m pytest test_calculator.py`，无需执行上面的安装命令。
它负责发现测试、调用测试函数和解释失败；不会替你决定哪些预期才符合需求。
少量一次性检查可以直接用 `assert`；有一组要反复执行的检查时，测试框架更便于组织与定位。
标准库也有 `unittest`；本章沿用 CS50P 的 pytest，不混用两套风格。

把 `test_calculator.py` 替换为最终数值测试版本，保留前面的正确 `calculator.py`：

```python
import pytest

from calculator import square


def test_positive():
    assert square(2) == 4
    assert square(3) == 9


def test_negative():
    assert square(-2) == 4
    assert square(-3) == 9


def test_zero():
    assert square(0) == 0


def test_str():
    with pytest.raises(TypeError):
        square("cat")
```

在两个文件所在目录运行：

```bash
python -m pytest test_calculator.py
python -m pytest -q test_calculator.py
```

`python -m pytest` 用当前环境的解释器启动框架；也可以用同一环境提供的 `pytest test_calculator.py`。
这里无需自己写 `main` 调测试函数，pytest 是调用者；测试函数不需要返回 `True`。
预期收集四个测试项并全部通过；两条正数断言仍算同一个测试函数，不是两个测试项。
`-q` 让报告简短些。报告中的 `.` 常表示通过，`F` 表示失败；准备/收集等阶段还可能出现 `E`。
读失败报告时先找失败测试名、断言行、实际值与预期值，再回到被测函数定位。

### 发现测试与拆分测试

通常从指定文件或目录开始，pytest 递归查找 `test_*.py` 或 `*_test.py` 文件，再收集 `test_` 开头的函数。
本章按默认规则命名；项目配置可以改变规则。`check_square` 不会仅因内部有断言就自动成为测试。
`python test_calculator.py` 只会定义函数；最终版本没有主动调用它们，因此不能用这个命令证明测试通过。
这些约定见 [pytest 测试发现文档](https://docs.pytest.org/en/stable/explanation/goodpractices.html#conventions-for-python-test-discovery)。

再次把乘法暂改为加法，运行 pytest，预期正数和负数测试失败。
默认情况下，一个测试函数失败后，其他已收集的测试仍会继续；不是“一条失败终止整场测试”。
但当前函数的后续断言不会运行；正因此要按行为类别拆分函数。
若使用 `-x`，框架会在首次失败后停止本轮测试；本章验证时不要加这个选项。
同一个测试函数中的多条断言适合检查紧密相关结果；独立行为更适合独立函数。

### pytest.raises：异常本身也可以是预期结果

先恢复正确乘法，再追踪上面 `test_str`：
1. pytest 调用 `test_str`；`pytest.raises(TypeError)` 创建一个用于检查异常的上下文管理器。
2. `with` 进入其检查范围，执行 `square("cat")`。
3. 字符串不能与字符串相乘，因此发生 `TypeError`；预期异常被检查并接住，这个测试通过。
4. 如果没有异常，测试失败；如果抛出不匹配的异常，测试也会失败。

`with` 是语句，管理一段代码的进入与退出；这里管理“是否出现预期异常”，下一章会用它管理文件关闭。
`raises` 是 pytest 提供的函数，不是 Python 关键字；匹配给定异常类型及其子类。
不要把被测调用写在 `with` 外；也不要只写 `square("cat") == TypeError`，异常不会变成可比较的返回值。
不要随便捕获 `Exception` 来让测试通过，否则拼错名字等错误也可能被当成合格结果。
本例依赖乘法运算自然抛出的异常，不是在 `square` 中额外编写所有类型校验。
接口边界必须先定：是否接受小数？是否接受布尔值？不能凭这个字符串用例宣称“所有非整数均被拒绝”。
准确机制参见 [pytest 断言与异常检查](https://docs.pytest.org/en/stable/how-to/assert.html)。

### Edge Cases：覆盖类别，不是追求堆数量

正数、负数、零分别代表本函数的重要输入类别；错误类型代表另一条执行路径。
**边界情况（edge case）**包括零、空值、上下限等容易被一般例子遗漏的位置；具体边界取决于契约。
选择案例前先手算预期，再写测试；不要把被测函数再调用一次当“预期值”，否则容易同错同过。
有限测试说明这些案例符合预期，不是数学证明，也不会自动涵盖文件、网络、交互输入等其他路径。

## 4. Testing Strings：打印与返回不是同一条数据流

先看独立可运行的 `hello_print.py`：

```python
def hello(to="world"):
    print(f"hello, {to}")


result = hello("David")
print(result)
```

运行 `python hello_print.py`，先输出问候，再输出 `None`。
原因是 `print` 对终端产生输出效果，而函数没有显式 `return`，调用结果便是 `None`。
因此 `assert hello("David") == "hello, David"` 不能检查这个实现的屏幕文字。
这不等于“打印不能测试”；pytest 有输出捕获工具，只是本章不需要它来测试字符串生成。

把数据处理与显示拆开，另建双文件例子的 `hello.py`：

```python
def main():
    name = input("What's your name? ")
    print(hello(name))


def hello(to="world"):
    return f"hello, {to}"


if __name__ == "__main__":
    main()
```

再创建 `test_hello.py`：

```python
from hello import hello


def test_default():
    assert hello() == "hello, world"


def test_argument():
    assert hello("David") == "hello, David"
    assert hello("Hermione") == "hello, Hermione"
```

运行 `python -m pytest test_hello.py`，目标是两个测试项通过，无需手动输入姓名。
现在的调用链：测试传入姓名 → `hello` 返回字符串 → 断言比较；交互分支才额外执行 `print`。
默认参数路径和显式参数路径分开检查；字符串的空格、逗号、大小写都属于精确输出契约。
改动验证：把预期中的逗号临时去掉，应能看到字符串差异，随后恢复。

## 5. Organizing Tests into Folders：目录与包

保持 `calculator.py`、`hello.py` 在练习根目录，将刚才两份测试文件移入 `test/`，不要保留重复副本：

```text
练习目录/
├── calculator.py
├── hello.py
└── test/
    ├── __init__.py
    ├── test_calculator.py
    └── test_hello.py
```

`test/__init__.py` 建为空文件即可，另外两份文件完整沿用上文；这是多文件目录示例。
从练习根目录运行 `python -m pytest test`，或运行 `python -m pytest` 让工具按默认规则搜寻。
`__init__.py` 将该目录作为常规 Python 包组织；导入包时会执行它，所以不要在其中放输入提示。
官方课堂使用这个文件组织测试；但“pytest 扫描任何目录都必须有它”不是普遍规则。
当前 pytest 也能发现无 `__init__.py` 的测试目录，包结构主要影响导入方式、名称与查找路径。
这里保留课堂包结构，避免把“测试发现”和“模块导入”讲成同一件事；见 [pytest 导入机制](https://docs.pytest.org/en/stable/explanation/pythonpath.html)。
若报 `ModuleNotFoundError: hello`，先核对当前工作目录、`hello.py` 文件名与解释器，不要先修改全局 `PYTHONPATH`。
不要把自己的文件命名为 `pytest.py`，它会妨碍正常导入第三方框架。

## 6. 自检、正式作业与覆盖核对

以下是简单自检，不是 CS50P 官方习题：
1. 读懂：解释为何错误加法对输入 `2` 仍然通过，以及什么输入能揭露它。
2. 跟写：不看正文写出正数、负数、零三类测试；说明谁调用这些函数、返回值来自哪里。
3. 改动：故意改错一个字符串预期，看到失败报告再恢复，证明确实执行到了该断言。
4. 独立做：给 `hello` 的空字符串输入新增一个测试；先明确是否应得到 `"hello, "`，再运行判断。
5. 验收：能说明测试解决什么、何时手工检查即可、为什么分开交互与返回值、如何从目录运行测试。
