## 2. 先回忆原来的文字请求

下面是调用片段，不是独立脚本：`HumanMessage` 从 `langchain_core.messages` 导入，`model` 是主示例中 `build_vision_llm()` 已创建的客户端。第 3 节的 `IMAGE_URL` 也沿用主示例配置。

```python
message = HumanMessage(content="你好，请介绍一下自己。")
response = model.invoke([message])
print(response.content)
```

这里有三个不同的对象：

| 对象 | 作用 |
|---|---|
| `model` | 已配置好服务地址、模型名称和密钥的模型客户端 |
| `message` | 准备发送给模型的一条用户消息 |
| `response` | 调用完成后得到的模型响应消息 |

`HumanMessage(...)` 创建消息，尚未发起模型请求。运行 `model.invoke([message])` 时才进入调用过程。最外面的列表表示“本次传入的消息列表”。

以前同样使用了 `content`，只是内容通常是一段字符串。

## 3. 多模态改了什么

你现在的核心代码是：

```python
message = HumanMessage(
    content=[
        {"type": "text", "text": "请描述图片中的主要对象。"},
        {"type": "image_url", "image_url": {"url": IMAGE_URL}},
    ]
)

response = model.invoke([message])
print(response.content)
```

变化集中在 `content`：它现在是一份内容块列表。

- 第一个字典是文本块，告诉模型要做什么。
- 第二个字典是图片块，提供图片输入。
- `type` 用于区分内容块的类型。

注意这里有两层列表，各自装的东西不同：

```text
[message]                 一组消息
    └─ message.content    这一条消息里的内容块
        ├─ 文本块
        └─ 图片块
```

把图片网址拼进普通字符串，只是在发送文字；按当前接口约定构造图片块，才是在声明图片输入。

## 4. 从运行程序到拿到答案

结合 `app/multimodal_vision_demo.py`，调用顺序是：

```text
load_dotenv()
  → 把 .env 中的配置加载到进程环境，默认不覆盖已有环境变量

build_vision_llm()
  → 读取模型名称、API 地址、密钥
  → 检查必填值
  → 创建模型客户端

HumanMessage(content=[...])
  → 组织文字和图片输入

model.invoke([message])
  → 客户端组织请求并调用配置的远程服务
  → 服务使用选定模型处理输入
  → 客户端返回响应消息

print(response.content)
  → 显示模型回答
```

客户端对象不是模型权重本身。此处在 Python 中创建客户端，不等于把视觉模型下载到自己的电脑上。

`response.content` 是响应的内容；当前示例主要读取文字回答，它不是图片的向量数组。其他模型或消息格式也可能返回内容块，不能把所有响应一概当作字符串。

## 5. 三个配置分别管什么

| 配置 | 你可以怎样理解 |
|---|---|
| `VISION_MODEL_NAME` | 请服务使用哪个模型 |
| `VISION_API_BASE` | 把请求发给哪家服务的哪个 API 入口 |
| `VISION_API_KEY` | 使用什么凭据访问服务 |

另外，`VISION_IMAGE_URL` 提供本次要处理的图片。

你之前指出过：OpenRouter 上也有 MiniMax，不能用 `model_name.startswith("google/")` 判断请求是否应该发往 OpenRouter。这个判断确实只检查字符串前缀。

现在的理解应当是：服务地址由明确配置决定，模型名称由该服务接受的模型 ID 决定。

三个字段非空，只能说明最基本的配置没有缺失。请求能否成功，还取决于凭据是否有效、模型是否支持图片、图片是否可读取，以及服务是否可用。

关于模型类：你讨论过 `ChatDeepSeek` 和 `ChatOpenAI`。它们是模型集成客户端，共享基础实现不意味着包版本必须相同，也不会让不支持视觉的模型自动获得看图能力。

## 6. 本地图片怎么传

在你当前讨论的兼容 Chat Completions 消息格式里，图片块的 `image_url.url` 可以承载两种不同来源：

```text
公网图片：HTTP(S) 图片地址 → image_url.url

本地图片：读取文件字节 → Base64 编码
         → 组成 Data URL → image_url.url
```

Data URL 的形状例如：

```text
data:image/jpeg;base64,后面是一段编码后的图片数据
```

因此，字段名称叫 `image_url`，不意味着只能使用公网网址。具体格式仍需服务和模型支持。

远程服务不能直接读取你电脑上的 `/Users/enkidu/photo.jpg`。只传路径，传出去的是路径字符串，图片文件本身没有过去。

Base64 是文件数据的编码方式，不是加密，也不是 Embedding 向量。

### 这是需要补讲的新知识

前面 JWT 章节提过编码名称，但没有教过“如何把本地图片变成消息输入”，所以这里不能当作已经学过。

`base64` 是 Python 标准库，无需安装；本节只用它的 `b64encode()` 函数把文件字节编码成文本可表示的形式。它不读图片内容、不识别物体，也不检查文件是否真是 JPEG。这里只要求会追踪转换，不要求背编码算法。

下面是**本地预处理片段**：先准备一张实际的 JPEG 图片，路径为当前工作目录下的 `photo.jpg`。不发网络请求，也不修改文件。

```python
import base64

with open("photo.jpg", "rb") as image_file:
    image_bytes = image_file.read()

encoded_bytes = base64.b64encode(image_bytes)
encoded_text = encoded_bytes.decode("ascii")
image_data_url = f"data:image/jpeg;base64,{encoded_text}"
print(image_data_url.startswith("data:image/jpeg;base64,"))
```

1. `"rb"` 表示按二进制读取，`read()` 返回 `bytes`（字节数据），不是图片路径。
2. `b64encode()` 接收原始字节，返回编码后的字节。
3. `.decode("ascii")` 按 ASCII 字符编码把编码结果变成 Python `str`，方便放入消息字典。它不是把图片解码成像素。
4. `data:` 表示字符串内含数据，`image/jpeg` 声明媒体类型为 JPEG，`;base64,` 表示逗号后是 Base64 内容。PNG 要用 `image/png`；只改后缀或声明不会转换图片格式。
5. 对真实 JPEG 文件，最后应打印 `True`；这只验证前缀拼接，不证明远程接口能接收图片。沿用第 3 节图片块，把 `IMAGE_URL` 换为 `image_data_url` 才是接入消息。

这解释了“文件字节 → 编码文本 → 消息字段”的连接。不要打印或记录完整图片编码；它可还原为图片内容。编码会增加体积，不是压缩。

来源：[Python 标准库 base64](https://docs.python.org/3/library/base64.html)。本地转换与供应商支持是两项独立验证。

## 7. 接上第 32 章：图片输入与向量模型别混在一起

第 32 章你练习的是“文本变向量”，当前章节练习的是“文字和图片交给视觉模型，获得回答”。

向量模型那条链路是：

```text
文本 → Tokenizer 分词并得到 token ID
→ 模型计算每个位置的隐藏向量
→ 按模型配置池化等处理
→ 文本向量
```

token 不必等于一个完整的词；token ID 是词表中的编号，编号本身不等于隐藏向量。模型处理后，每个 token 位置会有一条隐藏向量。

你重点弄清过平均池化：假设有 20 个有效 token，每个位置的向量为 768 维，则矩阵形状为 `20 × 768`。

```text
每一列有 20 个数
→ 这一列相加，再除以 20
→ 对 768 列分别做同样的事
→ 得到一条 768 维向量
```

除以 20 是因为每列参与平均的有 20 个数。真实批处理可能有 padding，需要按有效位置处理。

`batch_size` 控制一次处理多少条文本，不决定向量维度。例如 20 条文本、批量大小 8，可以分为 8、8、4 三批。

`SentenceTransformer` 封装文本编码流程，`torch` 是底层计算框架的 Python 导入名；它们都不等于向量数据库。

## 8. 接上第 31 章：请求和 State 的区别

你之前反复追踪过 Handoff 的调用链：

```text
模型提出转交工具调用
→ 框架运行 transfer_to_support
→ 工具返回 Command(update=...)
→ 框架更新共享 State
→ 下一轮模型调用前，中间件读取 State
→ 选择对应提示词和工具
→ request.override(...) 创建修改后的请求
→ handler(updated_request) 继续调用链
```

三个对象分别负责不同的事：

| 对象或调用 | 职责 |
|---|---|
| State | 框架保存的运行状态，例如 messages、active_agent |
| `request.override(...)` | 创建修改后的模型请求对象 |
| `handler(updated_request)` | 将新请求交给后续处理链，最终取得模型响应 |

远程模型不会自动拿到整个 Python State 对象。框架按模型接口组织消息、系统提示词、工具定义等输入。

当前图像示例可以看成更直接的调用：你自己构造 `HumanMessage`，然后交给 `model.invoke()`，没有加入上述角色切换流程。
