## 一、Python 与后端基础：00–07

### 第 00 章：环境配置

[回原章](../00_环境配置与PyCharm使用.md)

- Python 解释器负责执行代码；虚拟环境把本项目依赖与其他项目隔离；Poetry 管理项目依赖和运行环境。
- `poetry run python -m app.xxx` 是在项目环境中按模块执行代码。模块导入路径要与项目结构对应。
- 编辑器飘红与程序运行报错不是同一件事。先核对编辑器和终端是否使用同一个解释器，再检查依赖、拼写和类型。

### 第 01 章：Python 基础

[回原章](../01_Python基础.md)

- `name = value` 给名字绑定一个值，不需要 JS 的 `let` 或 `const`。大写常量名是约定，不会禁止重新赋值。
- `list` 保存一组有顺序的数据，`dict` 按键取值；例如 `messages[0]` 是取第一项，`state["question"]` 是按键取问题。
- 条件判断决定走哪个分支；`for` 逐项处理数据；函数的参数是输入，`return` 是把结果交回调用处。

```python
def route_question(state: dict) -> str:
    question = state["question"]
    return "research" if "知识库" in question else "answer"
```

先取问题，再判断是否包含“知识库”，最后返回两个字符串之一。这里没有调用模型，也不会因为返回了节点名就自行执行节点。

### 第 02 章：Python 进阶

[回原章](../02_Python进阶.md)

- 类定义一种对象的结构与行为；实例是按类创建的具体对象。`obj.name` 取属性，`obj.run()` 调用方法。
- 模块负责组织和复用代码；`import` 使另一个模块中的名称可用。定义函数与执行函数是两个步骤。
- `try/except` 处理异常；先看异常类型和最后一行信息，再沿 traceback（异常调用记录）找到自己的代码位置，不必逐字翻译整段英文。

### 第 03 章：Python 高级特性

[回原章](../03_Python高级特性.md)

- 列表推导式把“遍历、计算、收集结果”写在一起：`[text.strip() for text in texts]` 为每条文本去掉首尾空白，再组成新列表。
- `yield` 产出一个值并暂停，下一次继续时从暂停处往下走；不是普通的函数结束。
- 装饰器接收函数并返回处理后的对象，可以包装行为，也可以注册功能。`@tool` 不等于此刻执行工具。
- `with` 管理进入和退出代码块时的资源处理；离开代码块时执行退出逻辑，不是笼统地“销毁实例”。`async with` 是对应的异步版本。

### 第 04 章：FastAPI 基础

[回原章](../04_FastAPI基础.md)

- 路由把“HTTP 方法 + URL 路径”映射到一个函数。客户端请求命中路由后，框架才调用函数。
- 路径参数标识对象，查询参数常用于筛选，请求体携带提交的数据。它们都是输入，但位置和用途不同。
- 类型声明帮助 FastAPI 解析输入、做校验并生成接口文档；不是只给编辑器看的备注。

### 第 05 章：CRUD 与数据校验

[回原章](../05_FastAPI_CRUD.md)

- CRUD 就是增、查、改、删。接口需要同时考虑成功返回和“对象不存在、输入不合法”等情况。
- Pydantic 根据你声明的字段解析、校验外部数据，创建模型实例。它不是只能处理字典，也不是数据库 ORM。
- Pydantic 对象、Python 字典、JSON 文本是不同形态。`model_dump()` 得到字典；JSON 序列化才是转换成 JSON 表示。

### 第 06 章：SQLAlchemy ORM

[回原章](../06_FastAPI_ORM_SQLAlchemy.md)

- ORM 把数据库表与 Python 类关联起来，让你通过对象表达查询和修改，但底层仍执行 SQL。
- `Session` 管理一次工作中的数据库操作；`commit()` 提交事务；失败时要考虑回滚和资源释放。
- ORM 模型对应存储结构，Pydantic 模型约束接口输入输出。二者可以有相似字段，但职责不同。

### 第 07 章：代码分层

[回原章](../07_代码分层与模块化架构.md)

- 入口组装应用，router 接收 HTTP 请求，service 组织业务，数据访问代码处理存储。不要把所有职责塞进路由函数。
- `APIRouter` 中定义的接口需要注册到应用才能访问；只写文件不会自动出现接口。
- `Depends(...)` 由 FastAPI 在处理请求时解析并提供依赖，例如数据库会话或当前用户。不是你每次手动传入。

## 二、从模型调用到 RAG：08–15

### 第 08 章：提示词与聊天记忆

[回原章](../08_提示词工程与聊天记忆.md)

- 提示词说明模型要做什么；system、user、assistant 消息分别承担指令、用户输入和模型回复等角色。
- 模型不会因为上次回答过你，就天然记得下一次请求。应用需要保存并再次提供相关历史消息。
- 记忆不是无限追加；越长的历史越占上下文和费用，也越可能夹带无关内容。

### 第 09 章：RAG 与向量

[回原章](../09_RAG_向量数据库入门.md)

- RAG（检索增强生成）先找资料，再让模型依据资料回答；不是把新资料训练进模型参数。
- Embedding（向量表示）把文本表示为一串数字，以便按相似程度检索。向量不是能直接读懂的原文。
- 余弦相似度比较向量方向的接近程度；检索相近不保证事实正确，更不保证资料足够回答问题。

### 第 10 章：Chroma 向量数据库

[回原章](../10_RAG_ChromaDB向量数据库实战.md)

- 入库时保存文本、向量、ID 和元数据；查询时把问题向量化，再寻找相近记录。
- Collection 是组织记录的集合；元数据用于来源追踪和过滤，而不是向量本身。
- 文档和问题需要处在兼容的向量空间。换 Embedding 模型通常需要重新生成已有资料的向量，不能只看维度相同。

### 第 11 章：SQLite + Chroma 双存储

[回原章](../11_双存储架构SQLite_ChromaDB.md)

- SQLite 管业务记录和关系；Chroma 管相似检索。两套存储通过稳定的 ID 对应。
- 删除或修改文档时，要同步考虑正文和向量索引，避免“数据库已经删了，检索还返回旧内容”。
- 双存储不会天然共享一个事务，需要设计失败处理、重试或重建索引的办法。

### 第 12 章：FastAPI 接入 Chroma

[回原章](../12_FastAPI_Chroma_最小原型.md)

- 把本地检索能力包成 HTTP 接口：请求文本 → 校验 → 调用检索 → 返回结果。
- 接口层关心输入输出，检索层关心查询逻辑和存储；连接与模型的生命周期也要合理管理。
- 此时能返回相关切片，仍不等于已经完成生成回答的 RAG 闭环。

### 第 13 章：RAG 闭环

[回原章](../13_RAG_闭环_检索到回答.md)

```text
问题 → 检索相关切片 → 组织上下文和问题 → 调用模型 → 返回答案与来源
```

- 检索结果要真正进入模型请求，光把节点连起来或在终端打印资料不算传给模型。
- 没有证据时应明确说明依据不足，不能让模型用想象补齐。
- 排错先分段：没检索到、检索错了、资料没传进去，还是模型没按资料回答？

### 第 14 章：上下文窗口管理

[回原章](../14_上下文窗口管理.md)

- 上下文窗口是一次模型处理能容纳的 token 范围，不是应用数据库的存储上限。
- 历史消息、系统提示、资料、工具定义等都可能占用预算；还要为输出留空间。
- 截断、摘要和按需检索可以减少输入，但可能丢信息，所以要保留当前问题真正需要的内容。

### 第 15 章：LangChain 核心概念

[回原章](../15_LangChain核心概念.md)

- Prompt 组织输入，模型客户端发请求，输出解析器整理结果；链把这些步骤连接起来。
- `invoke` 执行一次调用，`ainvoke` 是异步调用入口。不同对象的输入结构不一定相同。
- 单独调用聊天模型常返回 `AIMessage`；调用 Agent 常返回包含 `messages` 等字段的状态结果，不能混为同一种返回值。

## 三、让应用更可靠：16–24

### 第 16 章：异步编程

[回原章](../16_异步编程深入.md)

- `async def` 定义协程函数；`await` 等待结果时可以让事件循环运行其他任务，不等于开启一个线程。
- 并发适合重叠网络等等待时间；Semaphore（信号量）用于限制同时执行的数量。
- `async with httpx.AsyncClient() as client` 管理客户端资源；同步阻塞操作不会因为放进异步函数就自动变成非阻塞。

### 第 17 章：JWT 用户认证

[回原章](../17_JWT用户认证.md)

- 登录校验通过后签发 token；后续请求携带 `Authorization: Bearer <token>`，后端验证后得到当前用户。
- 密码应保存哈希；JWT 签名用于检测篡改，不表示 payload 被加密，不能把秘密塞进去。
- 认证回答“你是谁”，授权回答“你能访问什么”。知道文档 ID 或 thread ID 不等于有访问权限。

### 第 18 章：WebSocket 实时通信

[回原章](../18_WebSocket实时通信.md)

- WebSocket 建立连接后可以持续双向传消息，适合实时聊天、房间消息和持续反馈。
- 需要处理连接、认证、收发和断开后的清理；不能只考虑连接成功的路径。
- 流式模型输出与 WebSocket 是两层能力：模型逐段产生文本，应用再通过连接转发给客户端。

### 第 19 章：Alembic 数据库迁移

[回原章](../19_Alembic数据库迁移.md)

- 迁移记录表结构怎样从旧版本变到新版本；修改 ORM 类不意味着已有数据库已同步修改。
- 自动生成迁移依赖正确的模型元数据，并且生成后仍要检查内容；空迁移不一定表示工具坏了。
- 迁移不是备份。删除字段等操作可能损失数据，降级也不保证自动恢复被删的内容。

### 第 20 章：pytest 测试

[回原章](../20_pytest单元测试.md)

- 测试按“准备条件 → 执行动作 → 断言结果”组织，检查行为，不只是代码能运行。
- fixture 提供可复用的测试资源；依赖覆盖可以隔离真实数据库或外部服务，避免测试依赖网络和费用。
- 成功、非法输入、权限失败和外部异常都值得覆盖。测试循环一次都没进入时，里面的断言也可能一次没执行。

### 第 21 章：进阶提示词

[回原章](../21_Prompt_Engineering进阶.md)

- 把任务、上下文、约束、示例和输出格式说清楚，比单纯要求“你必须专业”更可验证。
- 结构化输出后仍要解析与校验；模型说“这是 JSON”不代表字段和类型一定符合要求。
- 调整提示词或采样参数时固定测试问题，观察变化。temperature 低也不等于绝对正确或完全可复现。

### 第 22 章：AI 安全与伦理

[回原章](../22_AI安全与伦理.md)

- 用户输入、网页和知识库文档可能包含恶意指令，不能把资料中的命令当成系统授权。
- 权限过滤应在可信后端执行，尽量在检索阶段就限制可见资料，不能只提示模型“别泄密”。
- 工具执行要受权限约束；日志和公开文档不要记录 API Key、密码等秘密。模型输出仍需应用侧约束。

### 第 23 章：Chunking 切片策略

[回原章](../23_RAG_Chunking策略.md)

- 切片是把长文档拆成适合检索的片段；太小容易缺上下文，太大可能带入大量无关信息。
- Overlap（重叠）在相邻片段保留部分共同内容，降低边界断裂，但也会增加重复。
- 切片正文、向量、元数据是三件事。调 chunk 大小不是修改向量维度。

### 第 24 章：RAG 评估

[回原章](../24_RAG_评估与指标.md)

- 分开看检索有没有找到该找的资料、资料是否相关，以及回答是否有依据、是否答对问题。
- Top K 是最多召回的切片数量；阈值是过滤条件。不是 K 越大或阈值越低越好。
- 建立固定问题与参考依据，一次改一个变量，才能判断效果变化的来源，不能只凭一次“看起来不错”。

## 四、工具调用与流程组织：25–31

### 第 25 章：AI Agent 基础

[回原章](../25_AI_Agents基础.md)

- Agent 在模型判断与工具执行之间循环：模型决定下一步，程序负责执行和反馈。
- 工具给模型提供可调用的能力，例如检索；模型本身不会因为看到函数名称就拥有数据库连接。
- 并不是所有问题都需要 Agent。步骤固定时，普通函数或固定工作流也能完成任务。

### 第 26 章：Function Calling 执行循环

[回原章](../26_Function_Calling执行Loop.md)

```text
发消息和工具定义 → 模型返回工具名与参数 → 程序执行工具
→ 把工具结果交回模型 → 模型继续调用工具或给最终答案
```

- 工具定义描述“有什么工具、需要什么参数”；工具函数才执行实际操作。
- `tool_call_id` 把某次工具结果与对应的调用请求配对，不是用户 ID，也不是对话 ID。
- 多次调用工具就是重复中间的循环；要有执行边界，不能放任无限循环。

### 第 27 章：LangChain 对话记忆

[回原章](../27_LangChain对话记忆.md)

- 应用保存历史，并在合适的调用中恢复；模型看到的是此次传入的消息，不是自动读取你的全部数据库。
- 会话标识用于区分历史；它不代替登录认证，也不自动保证不同用户之间的数据隔离。
- 记忆保存与上下文裁剪可以同时存在：保存过的消息，不一定全部塞进每一次模型请求。

### 第 28 章：LangChain Agent 工具调用

[回原章](../28_LangChain_Agent工具调用.md)

- `create_agent` 组装模型与工具的执行流程；`@tool` 提供工具定义；调用 Agent 时由框架协调循环。
- 普通工具返回字符串时，标准工具执行流程会把结果包装成 `ToolMessage`，不要求每个工具自己手动追加历史。
- Agent 返回值通常是状态结果。需要最终文本时，要从结果中的消息取相应内容，不是把整个状态当字符串。

### 第 29 章：LangGraph 状态工作流

[回原章](../29_LangGraph状态工作流.md)

- State 是流转的数据；Node（节点）是执行工作的函数；Edge（边）规定下一步执行方向。
- `add_edge` 是固定连接；`add_conditional_edges` 在运行时根据路由函数结果选路。`compile()` 构建可执行图，`invoke()` 才启动一次执行。
- `START → model` 表示从 model 开始；`tools → model` 是工具后再调用 model，不是回到 START。

再区分三个你以前问过的对象：`TypedDict` 声明状态字典有哪些字段，不是运行时数据校验器；`llm.bind_tools(tools)` 给模型绑定工具说明；`ToolNode(tools)` 创建实际执行这些工具的节点。

```text
bind_tools：让模型知道可选工具及参数
→ 模型提出工具调用
→ tools_condition：路由函数，检查是否有工具调用，不是另一个模型节点
→ ToolNode：执行工具并产生工具结果
→ model：依据工具结果继续处理
```

```text
START → model → tools_condition
                  ├─ 有工具调用 → tools → model → 再判断
                  └─ 无工具调用 → END
```

判断发生在该次 model 节点返回之后。走 END 表示本次图执行结束，不是把还没生成完的回答强行截断。

Checkpointer 保存执行快照；`thread_id` 用于关联会话状态。`InMemorySaver` 是进程内存保存，不是关机后仍保留的磁盘数据库。`RunnableConfig` 描述执行配置，不是业务 State。

### 第 30 章：Dify 平台实战

[回原章](../30_Dify平台实战.md)

- 固定 RAG 流程是“用户输入 → 知识检索 → LLM → 输出”；Agent 方案则把检索封装成工具，由模型决定调用。
- 两种方案你都做过实践。要区分倒排/关键词检索和语义/向量检索：前者测试成功，不自动证明后者索引存在。
- Workflow API 由相应应用的凭据和接口定位，不是靠给请求填一个画布名称；你的 FastAPI 后端再把它封装成业务接口。
- Top K 是召回切片数量；最大迭代次数是 Agent 执行循环的上限，不是整个知识库数量，也不一定等于实际工具调用总数。

第四关请求处理的几个旧知识一起回忆：

```python
response.raise_for_status()
payload = response.json()
data = payload.get("data", {})
```

先检查 HTTP 错误状态，再把 JSON 响应解析成 Python 数据，最后取 `data` 键；键不存在才使用 `{}`。这一步是解析，不是把 Python 对象序列化为 JSON。HTTP 成功也不保证工作流业务成功，仍要检查返回内容。

`os.environ["KEY"]` 读取环境变量，不负责加载 `.env` 文件；缺少该变量会报错。`raise ... from exc` 则把新异常与原始异常关联起来，保留原因链。

### 第 31 章：Multi-Agent 与 Handoff

[回原章](../31_Multi-Agent与复杂工作流.md)

- Supervisor 负责协调，Subagent 负责分工任务；Router 根据条件选路；Handoff 是交接处理职责和必要上下文。
- 本章 Handoff 示例通过共享状态里的 `active_agent` 选择当前角色的提示词与工具，并不需要每次新建一个独立模型。
- `Command(update=...)` 表达状态更新；`request.override(...)` 创建本次模型调用的新请求；两者不是同一层的修改。

你反复梳理过的调用顺序是：

```text
1. 调用 Agent，框架准备当前状态与模型请求
2. 框架调用 apply_role_config(request, handler)
3. 中间件读取 active_agent，选择 prompt 和 tools
4. request.override(...) 生成修改后的请求
5. handler(新请求) 把执行交给后续处理链，最终到模型调用
6. 模型若请求 transfer_to_support，框架执行这个工具
7. 工具返回 Command，框架按更新规则写入 active_agent 和 ToolMessage
8. 下一次模型调用再次经过中间件，使用新的角色配置
9. 模型给出最终回复，或继续工具循环
```

`request` 和 `handler` 都由框架传入。`handler` 是可调用对象，不是模型回答，也不是修改 Agent 的永久配置。它返回后，中间件可继续处理结果，再返回给外层执行流程。

**模型收到的是从请求组织出的系统消息、对话消息、工具定义等，不是把完整 State 原封不动送给模型。** `active_agent` 由中间件读取并影响请求；自定义状态字段不会因此自动成为模型输入。

## 五、模型基础与当前章节：32–33

### 第 32 章：Hugging Face 生态

[回原章](../32_HuggingFace生态.md)

- Hugging Face 不只有向量模型，也承载不同任务的模型、数据集和相关工具。下载模型与通过远程 API 请求模型是两条使用路径。
- `sentence-transformers` 封装句向量等表示模型的加载和编码；`transformers` 提供模型与 tokenizer 等组件；`torch` 提供张量运算和模型执行能力。
- `Tokenizer` 根据对应模型的分词规则把文本变成 token，再映射成 token ID；ID 是编号，不是向量，也不是每个词固定只分成一个 token。

```text
文本 → tokenizer → token ID 序列 → 模型前向计算
→ 每个位置的隐藏向量 → 模型对应的池化/后处理 → 文本向量
```

在我们讨论的“取一层输出”的简化例子里，20 个 token 位置，每个位置一个 768 维隐藏向量，组成 **20 行 × 768 列**的矩阵。不是一个 token 必然对应很多个独立词向量。

**平均池化：每一列把有效 token 行的数相加，再除以有效 token 数，最后留下一个 768 维向量。** 如果 20 行全有效就除以 20；若有 padding，要用 mask 排除补齐位置。不是除以 768。

这里的旧术语只做简短提醒：**前向计算**是把输入送入模型算出输出；**隐藏向量**是模型内部某个位置的数字表示；**padding** 是为对齐批次长度而补的位置；**mask** 标记哪些位置有效。完整例子见 [Token 与 Pooling](../AI基础概念/01_文本进入模型_Token与Pooling.md)。

不同模型可能采用 CLS（取特殊 `[CLS]` 位置的隐藏向量）、最后一个有效 token 等方式，不能把平均池化强行套给所有模型。当前先理解它们都是“如何从位置表示得到整体表示”，不要求深挖所有架构。

调用封装中的几个参数也别混淆：

- `device` 是执行设备，例如 CPU 或可用 GPU；模型需要被实际放到相应设备上。
- `batch_size` 是一批处理多少条文本，不是 token 数，也不是向量维度；更大可能提高吞吐，也可能超内存/显存。
- `tier` 是项目代码选出的设备档位，供批量大小等配置使用，不是 Python 自动提供的变量。
- `str(getattr(model, "device", device))` 先取模型的 `device` 属性，不存在则用备用值，再转成字符串；它只是读取和格式化，不负责移动模型。

缓存持久化表示下载文件可以复用，不代表每次启动绝不访问网络；框架仍可能检查远端配置。也不要把 AI 帮你启动成功的容器算成你已掌握全部部署细节。

数学忘了可以回看：[向量与余弦相似度](../ai学习应用数学/01_向量与余弦相似度.md)、[从数字到平均池化](../ai学习应用数学/02_从数字到平均池化.md)。

### 第 33 章：多模态图像理解（尚未学完）

[回原章](../33_多模态AI_图像理解.md) · [详细复习](./33_多模态AI_学习复习.md)

你已经接触的核心变化是：**原来的消息只有文字，现在同一条消息的 content 可以包含文字块和图片块。**

```python
message = HumanMessage(content=[
    {"type": "text", "text": "请描述图片中的主要对象。"},
    {"type": "image_url", "image_url": {"url": image_url}},
])
response = model.invoke([message])
```

这是消息结构片段，沿用前面已创建的 `model`、`image_url` 和 `HumanMessage`，不是完整独立脚本。

1. 内层 `content=[...]` 装一条消息里的多种内容。
2. 外层 `invoke([message])` 装本次对话请求的消息列表。
3. 模型客户端把消息发到配置的服务，服务中的视觉模型处理图片和文字。
4. 返回的是响应消息，再读取 `response.content`；不应把所有可能的 content 都假设成纯字符串。

配置也各有职责：模型名选择模型，Base URL 选择服务入口，API Key 用于鉴权，图片 URL 指定图片。使用兼容接口并不代表任何模型都有视觉能力，实际要看所选模型与服务支持。

本地图片也能作为输入，但远程服务不能读取你的 `/Users/...` 路径。常见做法是读图片字节，编码为 Base64 data URL，再按服务支持的消息格式发送。**Base64 是编码，不是加密，也不是把图片转成 Embedding。**

Data URL 是把数据本身写进字符串的形式，不需要再去另一个网址下载。这里按新知识补了 [本地图片编码的具体步骤](./33_多模态AI_学习复习.md#6-本地图片怎么传)，不是要求你凭字段名猜用法。

本次校验已将 [示例文件](../../app/multimodal_vision_demo.py) 与讲义统一为 `ChatOpenAI`，服务入口参数为 `base_url`。这只是统一客户端，不保证所选远程模型支持图片；真实服务调用仍需单独验证。
