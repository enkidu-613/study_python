## 本章目标

上一章让客户端从 `/documents/1` 读到一份文档。本章关注服务端怎样保存这份资料、表达它属于谁，以及在一组写入只完成一半时怎样恢复一致。

固定数据是：

```text
documents = [
    {"id": 1, "title": "Python", "owner_id": 7},
    {"id": 2, "title": "HTTP", "owner_id": 7},
    {"id": 3, "title": "SQL", "owner_id": 9},
]
```

我们会在 SQLite 内存数据库中建立 `owners` 和 `documents` 两张表，通过外键描述归属，通过 JOIN 一起读取，再故意制造唯一性冲突，确认事务会把两次写入一起回滚。

## 先运行一遍完整实验

将代码保存为 `examples/cs-foundations/database_relations.py`。只使用 Python 标准库 `sqlite3`，无需安装依赖。数据库使用 `:memory:`，只存在于当前进程中。

```python
import sqlite3

connection = sqlite3.connect(":memory:", isolation_level=None)

try:
    connection.execute("PRAGMA foreign_keys = ON")
    print("foreign_keys:", connection.execute("PRAGMA foreign_keys").fetchone()[0])

    connection.execute("BEGIN")
    connection.execute(
        """
        CREATE TABLE owners (
            id INTEGER PRIMARY KEY,
            name TEXT NOT NULL UNIQUE
        )
        """
    )
    connection.execute(
        """
        CREATE TABLE documents (
            id INTEGER PRIMARY KEY,
            title TEXT NOT NULL UNIQUE,
            owner_id INTEGER NOT NULL,
            FOREIGN KEY (owner_id) REFERENCES owners(id)
        )
        """
    )
    connection.execute("CREATE INDEX documents_owner_id_idx ON documents(owner_id)")
    connection.executemany(
        "INSERT INTO owners(id, name) VALUES (?, ?)",
        [(7, "Avery"), (9, "Mina")],
    )
    connection.executemany(
        "INSERT INTO documents(id, title, owner_id) VALUES (?, ?, ?)",
        [(1, "Python", 7), (2, "HTTP", 7), (3, "SQL", 9)],
    )
    connection.execute("COMMIT")

    cursor = connection.execute(
        """
        SELECT documents.id, documents.title, owners.name
        FROM documents
        JOIN owners ON documents.owner_id = owners.id
        WHERE documents.id = ?
        """,
        (1,),
    )
    print("joined row:", cursor.fetchone())
    print("all rows:", connection.execute(
        "SELECT id, title FROM documents ORDER BY id"
    ).fetchall())

    try:
        connection.execute("BEGIN")
        connection.execute(
            "INSERT INTO documents(id, title, owner_id) VALUES (?, ?, ?)",
            (4, "RAG", 7),
        )
        connection.execute(
            "INSERT INTO documents(id, title, owner_id) VALUES (?, ?, ?)",
            (5, "Python", 9),
        )
        connection.execute("COMMIT")
    except sqlite3.IntegrityError as error:
        connection.execute("ROLLBACK")
        print("transaction failed:", type(error).__name__)

    cursor = connection.execute(
        "SELECT COUNT(*) FROM documents WHERE title = ?", ("RAG",)
    )
    print("RAG rows after transaction:", cursor.fetchone()[0])
finally:
    connection.close()
```

在仓库根目录执行：

```bash
cd examples/cs-foundations
poetry run python database_relations.py
```

若独立 Python 环境已激活，也可以从该目录运行 `python database_relations.py`。请先创建上面的完整程序，再执行命令。

精确输出：

```text

joined row: (1, 'Python', 'Avery')
all rows: [(1, 'Python'), (2, 'HTTP'), (3, 'SQL')]
transaction failed: IntegrityError

```

## 从重复数据到两张相关表

### 表和行

关系数据库把数据放在表中。表由列定义每个值的含义和约束，由行保存一条记录。这里 `owners` 保存所有者，`documents` 保存文档。一个文档的 `owner_id` 指向 `owners.id`，避免每份文档都重复写所有者姓名。

如果把姓名直接复制到每份文档，所有者改名时容易只改到部分记录；拆成两张表后，文档通过 ID 关联所有者。这个设计是关系建模的起点，不代表所有数据都必须拆表，也不在本章展开规范化规则。

`CREATE TABLE` 定义表；表一旦创建，后续 `INSERT` 才能往里面放数据。`CREATE INDEX` 创建索引。代码在创建完表后才插入数据，程序执行顺序是数据库能否接受这些语句的条件。

### 主键、外键与约束

`PRIMARY KEY`（主键）是表内标识某一行的列或列组合。本例的 `id INTEGER PRIMARY KEY` 让 owner 和 document 各有自己的标识。SQLite 会为整数主键提供行标识行为；主键值应被当作稳定身份，不要拿标题代替。

`FOREIGN KEY (owner_id) REFERENCES owners(id)`（外键）声明文档所有者必须能在 `owners` 表中找到。它约束两张表之间的引用关系，不会自动判断当前登录用户是否有权访问该文档。

SQLite 的外键检查要在每个连接上明确开启。本例创建连接后执行 `PRAGMA foreign_keys = ON`，并读取该设置验证结果为 `1`。这条设置必须在事务开始之前执行；连接是新的时要重新设置。不要依赖 SQLite 编译选项或默认值。

`NOT NULL` 禁止列值为空（SQL 的 `NULL` 表示缺少或未知的值）；`UNIQUE` 禁止受约束列出现重复值。`title TEXT NOT NULL UNIQUE` 意味着标题必须填写且不能重名。它是为了让后面的冲突可确定复现；真实知识库可能允许同名文档，届时应该改成符合业务定义的唯一约束。

约束由数据库检查。它能帮助阻止程序错误写入不一致数据，但不能替代 API 的输入校验、用户身份验证、访问控制或安全审查。

## 一次 JOIN 查询的数据怎样回来

查询使用 SQL：`SELECT ... FROM documents JOIN owners ON documents.owner_id = owners.id WHERE documents.id = ?`。`JOIN` 根据两边 owner ID 相等，把匹配的文档行与所有者行组合成查询结果。`WHERE` 把结果限制到 ID 为 1 的文档。

`?` 是参数占位符；真实值通过第二个参数 `(1,)` 传入。单元素元组末尾的逗号不能漏。值由 SQLite 驱动绑定，不要用 f-string 或字符串拼接把用户输入塞进 SQL。参数化既正确处理值，也能避免把数据误当 SQL 语句执行；它不能参数化表名或列名。

`sqlite3` 是 Python 标准库模块，为 Python 程序提供 SQLite 数据库接口。`sqlite3.connect(":memory:")` 创建连接实例，`:memory:` 表示临时内存数据库；`Connection.execute(sql, parameters)` 执行一条 SQL 并返回 `Cursor`（游标）对象。游标代表这次查询的结果读取位置。

代码直接调用 `connection.execute(...)`，这是连接对象提供的便捷接口，结果仍是游标。`fetchone()` 从结果集中取下一行；结果耗尽时返回 `None`。`fetchall()` 把剩余行作为列表返回。因此 `joined row` 是元组 `(1, 'Python', 'Avery')`，不是数据库连接对象，也不是字典。

如果需要处理很多行，通常逐行迭代游标，而不是把所有行一次装进内存。本实验数据只有几行，为了让输出可核对，才调用 `fetchall()`。

`executemany(sql, rows)` 是连接对象的方法，会把同一条参数化 SQL 对每组参数执行。例子用它录入 owners 和 documents；输入是参数元组组成的列表。不要误把它当作 SQL 语法，它是 Python DB-API 的调用方法。

失败分支中的 `sqlite3.IntegrityError` 是该模块的异常类，表示主键、唯一性、外键等完整性约束被违反。`type(error)` 是内置函数调用，取得这个异常对象的类；`.__name__` 读取类名字符串，所以输出 `IntegrityError`，不是查询结果。

## 索引：为查找增加一份结构

`CREATE INDEX documents_owner_id_idx ON documents(owner_id)` 为 owner ID 建立索引。索引是数据库额外维护的数据结构，帮助某些查询更快找到匹配行；本例也可能帮助按 owner ID 查文档或处理关联。

索引会占用额外存储；插入、删除或更新相关列时，数据库还要维护索引。因此不能给每一列都盲目建索引。表很小、过滤条件不合适、统计与成本判断不支持等情况下，SQLite 可能不使用某个索引；写了索引不等于每次查询一定走索引，也不保证一定更快。

可选检查：把查询改成按 `owner_id = ?` 筛选，再在 SQL 前加 `EXPLAIN QUERY PLAN` 查看 SQLite 的计划。输出会随 SQLite 版本、表大小、数据分布和统计状态而变化；练习只观察是否可能出现索引相关线索，不背固定输出，也不要只凭一行计划就判断实际性能。较大数据集应通过真实查询和测量验证。

索引只影响查找路径，不负责权限。即使 `owner_id` 有索引，应用仍必须检查当前用户是不是这份文档的所有者。

## 事务：把一组写入当成一件事

### 实验中发生了什么

`connection = sqlite3.connect(":memory:", isolation_level=None)` 中的 `isolation_level=None` 让连接不自动替我们开启常规事务，便于演示显式 SQL 边界。然后程序通过 `BEGIN` 开始事务，通过 `COMMIT` 确认成功写入，通过 `ROLLBACK` 放弃当前事务里的写入。

初始建表和插入资料也放在一组 `BEGIN` 与 `COMMIT` 之间。稍后失败实验在第二次插入标题 `Python`，但标题已有 `UNIQUE` 约束，所以 SQLite 抛出 `sqlite3.IntegrityError`。异常处理执行 `ROLLBACK`；第一次插入的 `RAG` 也一同撤销，查询结果为 0。

这就是原子性在本例里的作用：这一组操作要么整体提交，要么整体不留下。`try/except` 是 Python 的异常处理，不能替数据库回滚。本例的唯一冲突默认只让第二条插入语句失败，第一条 `RAG` 仍在未提交事务里；如果省略 `ROLLBACK` 并在随后误执行 `COMMIT`，第一条仍可能被保存。因此程序明确回滚整组操作，而不是假定“发生异常就已经全部撤销”。

事务也有隔离性等其他性质。隔离涉及多个并发事务同时读写时彼此能观察到什么，具体保证与数据库和事务配置有关。本章用一个连接演示事务边界，不声称完整覆盖并发隔离级别、锁或竞态条件。

### 为什么不用连接的 `with` 代替关闭

`sqlite3.Connection` 的上下文管理器 `with connection:` 在代码块结束时根据异常提交或回滚事务，但它**不会自动关闭连接**。本例使用 `isolation_level=None` 并显式执行 `BEGIN`、`COMMIT`、`ROLLBACK`，外层 `try/finally` 最终调用 `connection.close()`，让事务边界和资源关闭一目了然。

在常规默认事务模式中，未提交的改动若直接 `close()`，可能回滚而不是替你提交。因此不能把“离开 with”误读成“连接已关闭”，也不能把“关闭连接”当作成功提交。事务何时开始、何时提交、失败如何回滚，都应明确。

本例选择显式事务控制是为了教学，不是所有项目都必须写原始 `BEGIN`。实际项目可以采用连接上下文管理器或框架的事务 API，但要弄清它管理的是事务还是连接生命周期，以及其自动提交行为。

## 跟写与失败边界

跟写一：在查询里把参数从 `(1,)` 改成 `(3,)`。预测并验证结果变为 `(3, 'SQL', 'Mina')`。这确认参数值影响 `WHERE` 条件，而 SQL 结构本身没有拼接变化。

跟写二：将第二次插入的标题从 `Python` 改成 `Notes`。此时没有唯一冲突，程序会提交两条新记录；若之后想再次观察失败回滚，请恢复成 `Python` 并重新运行完整程序。由于数据库是内存库，每次启动都会从干净状态开始。

边界检查：把一个新文档的 `owner_id` 改成 `404`，应触发外键约束错误。若修改代码去捕获此异常，也必须回滚当前事务；否则程序会在异常后留下未处理事务。

不要把这些写入指向项目真实业务库。本例 `:memory:` 是重要的安全边界，不要为了“方便看结果”擅自换成业务数据库路径。

## 独立练习

在本例中为 `documents` 新增 `summary TEXT NOT NULL` 列，为三份固定数据分别填写简短摘要；查询 `/documents/1` 对应的记录时，同时取回标题、摘要和所有者姓名。

验收标准：

- 每份文档都有摘要，数据库会拒绝缺失摘要的插入。
- 查询文档 1 得到标题 `Python`、你写入的摘要和所有者 `Avery`。
- 把 owner ID 改为不存在的值会被外键拒绝。
- 用一个已存在的标题触发唯一性冲突后，本次事务中先写入的新记录也不存在。
- 仍只用内存数据库和标准库，不依赖本章以外临时生成的文件。

提示：先调整建表列，再调整 `INSERT` 的列名、占位符数量、每组参数和 `SELECT` 字段；四处数量要一致。独立练习不附完整答案。

## 本章边界与四条检查

本章学到表、主键、外键、`NOT NULL`、`UNIQUE`、JOIN、参数化、游标读取、索引和显式事务的基本用途。不学复杂范式设计、视图、触发器、迁移、SQLite 文件部署、锁策略、并发隔离级别、备份恢复或 PostgreSQL/MySQL 运维。

事务不是备份：误提交的数据仍可能需要恢复方案；内存实验也没有磁盘持久化。索引不是权限控制。SQLite 是轻量关系数据库，不代表所有生产服务都应选择 SQLite。

四条理解检查：

1. 为什么用 `owners` 表和 `documents.owner_id`，而不是每行都重复保存姓名？
2. 外键能保证什么，不能替代哪类用户访问检查？
3. 唯一冲突后为什么 `RAG` 也不见了？哪个语句界定了这组写入？
4. 索引为什么可能加速查询，却不能保证查询一定使用它？

## 小结与衔接

一句话：关系表用键关联实体，约束保护数据形状，索引为部分查找增加维护成本换取潜在速度，事务让多步写入按整体提交或撤销。
