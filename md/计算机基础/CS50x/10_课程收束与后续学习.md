## 复盘同一条目录功能

需求：用户输入 HTTP，只看标题匹配的知识文档。先区分两种实现，避免把同一名字“筛选”误当成同一机制。

### 浏览器本地过滤

08 章的静态 HTML 有三个已经写进页面的 tr。输入事件触发 JavaScript，读取 DOM 文字并隐藏不匹配行。数据从哪里来？HTML 文件。关闭页面后没有写入变化。它不请求网络、不查 SQLite，也不限制用户能看到的数据。

### Flask 服务端过滤

09 章访问 /?q=HTTP 时，浏览器发送 GET；Flask route 从 request.args 读取 q，执行 SQL WHERE title LIKE ?，模板把结果输出为 HTML。数据源是隔离的 SQLite demo 文件。授权逻辑必须在服务器端，不能相信浏览器隐藏的行或表单字段。

调用链追踪：

| 顺序 | 部件 | 输入 | 处理 | 可观察结果 |
| --- | --- | --- | --- | --- |
| 1 | 浏览器表单/URL | q=HTTP | 生成 GET 请求 | Network 面板看到方法与查询串 |
| 2 | 网络与 HTTP | 主机、路径、参数 | 寻址、传输、请求解析 | Flask 收到 request |
| 3 | Flask 路由 | 方法 GET、路径 / | 调用 index() | 视图函数开始执行 |
| 4 | Python 视图 | request.args["q"] | 调用 get_db() | g 中有本请求连接 |
| 5 | SQLite | 查询和绑定值 | 匹配标题行 | 结果列表，不是 HTML |
| 6 | Jinja | 记录列表、搜索串 | 转义变量并渲染 | HTML 响应正文与 200 状态 |
| 7 | 浏览器 | HTML 响应 | 构建 DOM、计算 CSS、绘制 | 用户看到匹配项 |

变量的生命周期也不同：输入框的 DOM 引用活到当前文档卸载；request 代理在一次请求上下文中解析到当前请求；g.db 只属于当前应用上下文并在 teardown 关闭；SQLite 文件则比一次请求活得更久。说清“谁拥有数据、活多久、谁会读取”比只记一串 API 名称更可靠。

## 可运行复习：输入、处理、输出

这个短程序用 Python 标准库和内存中的数据演练课程最核心的计算模型：取输入、筛选、排序、给出输出。它不需要 Flask 或 SQLite。

文件：examples/cs50x/course_review.py。仓库根目录运行：

~~~bash
cd examples/cs50x
poetry run python course_review.py
~~~

命令使用项目现有 Python 3.12+ Poetry 环境。预期输出：

~~~text
查询：HTTP
2 | HTTP 请求 | owner 7
匹配数量：1
~~~

~~~python
DOCUMENTS = [
    {"id": 1, "title": "Python 入门", "owner_id": 7},
    {"id": 2, "title": "HTTP 请求", "owner_id": 7},
    {"id": 3, "title": "SQL 查询", "owner_id": 9},
]


def search_documents(documents, query):
    normalized_query = query.strip().casefold()
    matches = [
        document
        for document in documents
        if normalized_query in document["title"].casefold()
    ]
    return sorted(matches, key=lambda document: document["id"])


def main():
    query = "HTTP"
    matches = search_documents(DOCUMENTS, query)
    print(f"查询：{query}")
    for document in matches:
        print(
            f"{document['id']} | {document['title']} "
            f"| owner {document['owner_id']}"
        )
    print(f"匹配数量：{len(matches)}")


if __name__ == "__main__":
    main()
~~~

### 逐段追踪

1. 解释器创建 DOCUMENTS 列表；每个字典表示一条记录。它只是内存里的课堂样本，不连项目数据库。
2. main() 把 "HTTP" 传给 search_documents。函数收到两个参数：原始记录集合和查询字符串。
3. strip() 去掉两端空格，casefold() 生成适合不区分大小写比较的字符串；原始标题不被修改。
4. 列表推导式逐个读取字典的 title，若规范化后的标题包含规范化查询，就把整条字典放入 matches。
5. sorted 返回按 id 排序的新列表，不会原地改写输入 DOCUMENTS。
6. main 打印查询值、每条记录和数量。这个顺序就是输入 → 处理 → 输出。

### 看懂列表推导式与排序 key

表达式 `[document for document in documents if 条件]` 是列表推导式（list comprehension）：按顺序从 `documents` 取出一个元素，把它暂时叫作 `document`；检查 `if` 条件；条件为真时把该元素放进新列表。它与下面的循环等价，先读懂循环版本也完全可以：

~~~python
matches = []
for document in documents:
    if normalized_query in document["title"].casefold():
        matches.append(document)
~~~

`sorted(matches, key=lambda document: document["id"])` 中的 `key` 是排序依据函数。`lambda document: document["id"]` 是一个匿名的小函数，接收一条记录并返回它的 id；`sorted` 对每条记录调用它，用返回的数字比较顺序，但最终仍返回原来的记录字典组成的新列表。它不把字典替换成 ID，也不修改 matches。等价的命名函数形状是 `def document_id(document): return document["id"]`，再传 `key=document_id`。数据少或排序逻辑简单时 lambda 简洁；逻辑复杂时命名函数更易读。

不要把 Python 中列表推导式与 SQL 的查询引擎混成一个东西：它们表达相似筛选条件，但数据位置、扩展能力、并发访问和持久化不同。三条数据用 Python 列表最直接；数据库拥有大量持久记录时，应该让数据库执行查询。

### 改动验证

- 把 query 从 HTTP 改为 python：数量应为 1，输出 id 1。
- 改为三个空格：strip() 后查询为空字符串；Python 中空字符串包含于每个字符串，因此会匹配三条。若业务不想把空查询解释为“全部”，应该在函数入口明确规定空查询结果，而不是假设它自然为零条。
- 改为 unknown：数量为 0，不打印任何文档行。
- 在调用后打印 DOCUMENTS：输入顺序与内容不变，验证 sorted 返回新列表。

这个练习的输出是可观察证据，但不等于完整测试。若代码未来被复用，可用 unittest 为空查询、无匹配、大小写、排序等边界写断言。

## 测试：用证据代替“我看了一眼”

测试是对可重复输入和预期行为的检查，不会证明程序对所有可能输入都正确。课程里见过几种不同层次：

- 手动检查：适合先看 UI 和浏览器 Network/Console，成本低，容易漏掉边界。
- 函数级测试：输入小数据，断言输出。适合 search_documents 的空查询和大小写边界。
- 集成测试：像 09 章 Flask test_client，从 HTTP 方法/路径穿过 route 到临时 SQLite，再检查响应状态和正文。
- 端到端测试：通过真实浏览器操作前端和服务器，覆盖真实交互，较慢且维护成本更高。

先确定契约：输入是什么、成功/失败时输出是什么、副作用在哪里。测试应覆盖正常路径、边界值、非法输入和安全关键分支。若把 owner_id 从 session 改成用户提交的表单值，测试必须抓出“用户可伪造所有权”的授权漏洞；只断言页面有 200 不够。

调试时先复现，再缩小范围：记录输入和期望；看错误发生在浏览器、HTTP、route、SQL 还是模板；构造最小输入；一次改一处；重跑同一验证。改变结果的最小修复比大段重写更容易验证。

## 可读性、设计与维护

设计（design）不只指视觉样式，也包括函数边界、命名、数据模型、错误路径和调用者契约。可读程序让维护者能回答：值从哪里来？谁修改它？失败时返回什么？谁负责释放资源？

- 命名用 owner_id、normalized_query 这类能说明角色的词；避免 x、data2 让读者猜测。
- 函数尽量有明确输入输出和单一职责。把查库、权限判断、HTML 拼接全部塞进一条巨大 route，会让每种错误难以独立测试。
- 处理失败值：找不到路由是 404，输入非法可返回 400，数据库不可用不能伪装成“查无记录”。
- 避免重复业务规则。如果 HTML 限长 80 字、服务器却允许任意长度，用户能绕过浏览器直接发请求。权威校验在服务器。
- 为重要行为写少量解释性注释，说明“为什么”而不是复述代码表面动作。
- 把复杂度留在需要它的地方：静态页面不必引入 Flask；三行内存列表不必强行上数据库；数据持久化、多人访问或 SQL 查询需求出现后，数据库才带来清晰收益。

维护意味着程序不仅今天跑通，也能在输入变化、依赖更新、数据增长或维护者更替时被理解和修改。文件布局、依赖说明、启动方式、测试命令和安全限制都属于程序的交付面。

## 计算资源和现实约束

任何算法都运行在有限机器上：CPU 时间有限，RAM 有限，磁盘/数据库容量有限，网络可能慢或断，能耗与云账单有限，人的注意力和维护时间也有限。

对三条记录，线性扫描几乎没有成本；有数百万行时，同样的扫描、排序或重复读取会造成明显等待。应该先用真实规模测量，再决定索引、缓存、分页或更合适的数据结构。哈希表通常提供快速查找但占额外内存；排序后可二分查找但维护更新有成本；索引加速特定查询但占磁盘并减慢写入。没有脱离输入规模与访问模式的“永远最快”。

内存同样受限：C 中 malloc 失败必须检查，拥有的内存最终要 free；Python 对象更方便，但大型文件若一次全部载入仍可能耗尽 RAM。Web 响应也有限：一次返回百万行会增加数据库、网络、浏览器内存和用户等待成本，分页与结果上限是产品和资源共同的设计问题。

网络请求可能超时或重试；因此改变状态的操作要考虑重复提交。数据库写操作要考虑事务边界。服务器容量有限，因此输入长度、并发、查询时间和外部 API 费用要有明确上限。安全也有资源取舍：日志需可诊断，但不应记录密码或 session secret；数据保留越久，泄露影响越大。

### 资源评估练习

对目录应用的“搜索全部文档”功能，分别估算只有 3 条、10 万条、1000 万条时：

1. 数据储存在哪里？每次请求是否把所有行加载到 Python？
2. 标题搜索是否能利用索引？LIKE '%词%' 与前缀搜索的成本是否相同？
3. 响应是否应该限制条数/分页？用户一次实际需要多少结果？
4. 对测试与运行环境分别记录数据量、等待时间、内存或查询计划，避免凭直觉说“够快”。

回答可以是数量级判断，不要求先做数学推导。重要的是明确约束和测量方式，不假装数据规模没有上限。

## 安全、伦理与程序责任

程序接受输入、保存数据并影响用户；技术“能做”不自动意味着“应该做”。设计时考虑：用户是否知道收集什么？是否有必要？谁能访问？多久删除？误判如何纠正？页面对辅助技术是否可用？泄露或错误结果由谁承担？

最小安全基线：服务端验证输入；SQL 用参数绑定；模板转义不可信内容；服务器执行对象级授权；用 HTTPS 保护传输；秘密用环境变量/secret manager；改状态的表单处理 CSRF；错误页不泄漏堆栈；日志避开凭据；依赖只加有理由的包并及时检查更新。

测试与伦理也相关：测试样本是否代表不同用户？自动分类错误会伤害谁？模型/规则置信不足时是否能申诉或转人工？采集真实数据前先问是否可使用、是否含个人信息，并用合成数据做课程实验。CS50 学术诚信要求以官方政策为准；学习中可用课程允许的工具解释概念，但提交必须体现自己的理解和独立工作，不能把他人或 AI 生成的完整答案冒充个人成果。

## 独立复盘任务

不看代码，写出 HTTP 查询从 URL 到 SQL 结果再到 HTML 的七步调用链；每步说明输入、执行者和输出。然后对复习程序独立加一个 owner_id 过滤参数，保持排序稳定，列出空结果与无效 owner 的预期输出。

验收标准：能跑程序；搜索大小写和空字符串的边界符合你定义的契约；没有改写输入记录；说明静态前端过滤与服务器查询的不同；指出样例中哪些安全措施仍缺失。错误定位提示：先把输入、函数返回值和最终打印分开检查，不要先把全部逻辑重写。
