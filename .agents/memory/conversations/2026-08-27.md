## 对话 98: 遗忘曲线功能决策、FSRS 算法与 review-scheduler 技能实现

时间: 2026-08-27

### 项目是否适合加遗忘曲线功能（决策过程）

- 结论：适合。项目已有 `history-archiver`（归档对话）和 `chapter-review-quizzer`（章节测验）两个技能，缺的正是"什么时候复习"的调度环节，遗忘曲线功能补上这一环。
- 数据基础已具备：`.agents/memory/conversations/` 下 40+ 天的对话记录 + `learning_history_index.json` 的 89 条结构化条目，就是现成的学习历史数据源。

### FSRS（Free Spaced Repetition Scheduler）算法

- 基于记忆三状态建模：难度 D（材料难不难）、稳定性 S（记忆能撑多久）、可提取性 R（现在还能想起来的概率）。
- 核心思想：每次复习评分后更新三状态，预测"回忆概率降到约 90% 的时刻"作为下次最佳复习时间——太早复习浪费时间，太晚复习等于重学。
- 对比传统 SM-2 艾宾浩斯固定间隔：FSRS 间隔是按每个人的遗忘数据动态拟合的，不是固定 1/3/7/15 天。

### 动态档位调整（AI 对话 → FSRS 评分映射）

- 可行方案：从与 AI 的学习对话中提取信号映射到 FSRS 评分——用户明说"我忘了/X 是什么来着"→ again（评分 1）；答对测验/主动正确引用旧概念 → good（评分 3-4）；全新概念 → 入队新卡。
- 挂钩点在 `history-archiver` 归档流程：归档对话时顺带扫描学习信号，更新记忆状态。

### 封装为技能（skill）的决策

- 适合封装：skill 规范本身就包含"可调用的脚本"，复习调度有明确 CLI（`add`/`due`/`rate`/`list`/`stats`/`migrate`），天然符合。
- 实现：`app/tools/review_scheduler.py`（FSRS 逻辑）+ 三端技能定义（`.trae/skills/review-scheduler/`、`.reasonix/skills/review-scheduler/`、`.codex/skills/review-scheduler/`）。
- 关键决策：旧 `.trae/memory/review_queue.json`（7 月阶梯版错题队列，schema 被测试锁定）只读不动；FSRS 用新文件 `fsrs_queue.json`，通过 `migrate` 命令迁移 14 条旧错题。
- 踩坑修复：迁移的新卡（`state=New`）首次复习前 `stability`/`difficulty` 为 None，格式化输出报错——输出时判 None 显示"新卡"/"-"。

### MPS 与 ANE 澄清（设备知识）

- MPS（Metal Performance Shaders）跑在 **GPU** 上，与 ANE（Apple Neural Engine）无关。
- PyTorch 的 MPS 后端通过 Metal 用 GPU，**无法访问 ANE**；用 ANE 需转 Core ML。
- 本项目 512 维 BGE 小模型，MPS 已达毫秒级编码，无需 Core ML 转换。

## 对话 99: 第 33 章多模态——VLM 选型、OpenRouter 配置与首次成功运行

时间: 2026-08-27

### 第 33 章学习内容与心智模型

- 链路变化：`文本 -> tokenizer -> 模型` 变为 `文字 + 图片 -> 多模态消息 -> 视觉语言模型(VLM) -> 文字回答`。
- 多模态消息形态：`content` 从字符串变为**内容块列表**——`{"type": "text", ...}` 文本块 + `{"type": "image_url", "image_url": {"url": ...}}` 图片块。
- 关键区分："消息格式正确" ≠ "模型能看图"——视觉能力取决于模型本身，`MODEL_NAME` 能生成文字不代表能看图。

### VLM 选型（要求：合适且便宜）

- OpenRouter 免费视觉模型清单（`input_modalities` 含 `image` 且价格 0）：`google/gemma-4-31b-it:free`、`google/gemma-4-26b-a4b-it:free`、`minimax/minimax-m3:free`、`nvidia/nemotron-3-nano-omni-30b-a3b-reasoning:free` 等。
- 免费模型限制：上游共享池限流（429）、不稳定，选 `:free` 后缀模型需容忍重试。

### .env 配置与多 Provider 支持

- 新增配置：`VISION_MODEL_NAME`、`VISION_IMAGE_URL`（演示图片 URL）、`OPENROUTER_API_KEY`、`OPENROUTER_BASE_URL`。
- 修改 `app/multimodal_vision_demo.py` 的 `build_vision_llm`：优先级 `VISION_API_KEY / VISION_API_BASE`（视觉专用）→ `OPENROUTER_API_KEY / OPENROUTER_BASE_URL`（模型 ID 含 `:free` 或 `google/` 前缀时自动切换）→ `MODELSCOPE_API_KEY + MODEL_API_URL`（项目默认）。

### 运行排查（429 → 成功）

- 首选 `google/gemma-4-31b-it:free` 连续 429：Google AI Studio 上游共享池临时限流（`limit_source: upstream_provider_shared_pool`），非配置错误。
- 换 `google/gemma-4-26b-a4b-it:free` 同样 429（Google 系全限流）。
- 换 `minimax/minimax-m3:free` **成功**：正确描述博客横幅（动漫角色、百合花、长柄武器、水面场景），并按要求区分"最确定/最不确定"内容。最终 `.env` 定格 `VISION_MODEL_NAME=minimax/minimax-m3:free`。

### Zed 显示"排除文件"的原因

- Zed 的 AI 上下文收集默认排除 `.env`（防止 API Key 等敏感信息发给 AI 提供商），是安全特性。
- 不影响手动编辑和语法高亮；不建议关闭该排除。

## 对话 100: 多模态图片输入与 OpenRouter 配置简化

时间: 2026-08-27 23:29 - 2026-08-28 00:32（按对话开始日期归档）

### 对话摘要

- 解释 `model_name.startswith("google/")` 是字符串前缀判断，只能识别 Google 模型，不能代表所有 OpenRouter 模型；MiniMax 模型名称通常不会满足这个条件。
- 检查并简化第 33 章视觉模型示例：删除基于模型名称猜测供应商的 `startswith()` 与 `:free` 判断，改为显式读取 `VISION_MODEL_NAME`、`VISION_API_KEY`、`VISION_API_BASE` 和图片 URL。
- 说明多模态图片输入不只有一种协议格式。在当前 OpenAI-compatible Chat Completions 链路中，最通用的是 `type: "image_url"`；它的 `url` 可以是公网 HTTP(S) 地址，也可以是本地图片经过 Base64 编码后的 `data:image/...;base64,...` Data URL。
- 明确本地文件路径不能直接发送给远程模型；本地图片需要“读取字节 → Base64 → Data URL → `image_url.url`”，或者先上传到可访问的对象存储地址。
- 第 33 章相关示例测试通过，项目全量测试结果为 37 passed；未执行真实视觉 API 请求。
