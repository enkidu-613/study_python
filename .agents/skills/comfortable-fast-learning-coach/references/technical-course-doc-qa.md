# 技术课程教学文档 QA

本参考用于编写、重写、审查或验收技术课程教学文档。它把外部教学文档审查思想提炼成项目内规则，不要求安装或调用对应的外部 Skill。

## 何时读取

只有在以下任务中读取本文件：

- 新写或重写一章技术教程；
- 用户要求检查教程是否完整、适合自己、能否实际走通；
- 教程同时绑定项目代码、测试、命令或部署步骤；
- 连续章节设计完成后做一次整体质量检查。

普通概念解释、单个报错、考试批改不需要加载完整 QA 流程。

## 四层审查栈

按下面顺序审查，前一层暴露的问题会影响后一层；不要用后一层的漂亮措辞掩盖前一层的路径缺陷。

### 1. 教学路径审查

检查学习者能否从当前起点走到本章目标：

- 起点、前置知识和本章目标是否明确；
- 新术语是否先给真实代码形态，再解释抽象概念；
- 每个命令和代码步骤是否有输入、动作和可观察结果；
- 是否在一个小闭环完成后才引入下一个抽象；
- 是否明确本章不学什么，避免把后续知识伪装成当前必需；
- 所有命令、示例代码和版本假设是否实际执行过。

未实际执行的命令只能标记为“待验证假设”，不能写成确定的操作结论。

### 2. 学习体验审查

检查学习者是否有机会形成理解，而不是只读到很多信息：

- 一段是否只承担一个主要新概念；
- 是否有“看、追踪、跟写、改动、独立做”的动作；
- 是否解释为什么使用当前方案，以及何时不需要它；
- 是否覆盖最容易造成知识断层的变量、生命周期、输入输出和边界；
- 练习是否能用结果验证，而不是用“看起来懂了”结束；
- 文档是否符合当前学习者的节奏，不因为补充资料而变成百科全书。

用户已经反复问过的阻塞点应回写正文；一次性语法摩擦、与当前链路无关的联想和后续高级问题应留在困惑记录或边界说明中。

### 3. 技术严谨性审查

把文档中的断言拆出来检查：

- 术语是否准确，类、函数、实例、装饰器产物和协议对象有没有混称；
- “必须、永远、自动、完全、只要”等绝对词是否真的成立；
- 结论是否适用于当前项目锁定的依赖版本；
- 官方文档、代码实现、测试结果和文档描述是否一致；
- 每个外部来源是否真的支持对应断言；
- 例子有没有省略会改变行为的前置配置、导入、权限或环境变量。

严重事实错误、会导致数据泄露或破坏环境的错误标记为 `BLOCKER`；会阻塞理解或造成错误使用的标记为 `WARNING`；不影响执行但存在歧义或表达改进空间的标记为 `OBS`。

### 4. 项目可执行性审查

只有当教程绑定代码仓库时才启用这一层：

- 文档里的文件路径、函数名、依赖名与仓库真实内容一致；
- 运行命令的工作目录、环境变量和端口真实存在；
- 示例代码与测试验证的是同一个契约，而不是两套相似逻辑；
- 依赖版本、数据库迁移、持久化目录和外部服务边界写清楚；
- 能运行的 happy path 尽量放入测试或 CI；
- 失败路径至少有一个可复现的检查点。

这一层是条件审查，不要求每个纯理论章节都创建测试工程。项目型章节中，代码仓库是事实来源；若文档与代码冲突，先记录冲突并核对版本，不凭感觉改写其中一方。

## 审查输出格式

审查时优先列问题，不先写长篇总结。每项包含：

```text
[BLOCKER|WARNING|OBS] 位置：具体问题
证据：文档、代码、测试或官方来源中的对应事实
影响：学习者会误解什么，或运行时会发生什么
建议：最小修补动作
```

顺序固定为：事实/安全/可执行性 -> 学习路径 -> 术语和表达 -> 可选润色。

没有问题时明确写“未发现阻塞问题”，并列出尚未验证的命令、外部 API 或依赖版本，不能把未验证说成通过。

## 与现有学习流程的关系

本 QA 参考不替代学习教练：

- 学习教练决定章节边界、难度、练习和复习节奏；
- 本参考审查教程是否真的可教、准确、可执行；
- `review-task` 的能力只在教程有对应项目代码时启用；
- 不因为审查发现问题就自动把章节标记为已完成；完成仍需学习者通过四条理解标准并完成实际验证。
